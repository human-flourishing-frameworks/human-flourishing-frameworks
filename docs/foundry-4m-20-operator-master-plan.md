# Foundry 4M / 20-Operator Master Plan

Status: execution plan / assumptions explicit / not proof of revenue.

## Plain Claim

The Founder wants to start now with 20 operators and build toward a 4M target.

This document treats `4M` as a revenue/runway target unless the operator later
redefines it. If `4M` means four months instead, use the same plan as a 120-day
execution clock and ignore the dollar math.

This is not current traction, not committed revenue, not investor evidence, not
a guarantee, and not proof that a foundry resource pool is implemented. It is a
bounded operating plan.

## Anti-Hallucination Locks

Do not claim:

```text
20 operators are already active
4M revenue is already won
foundry pooling is implemented
operators consented to resource sharing
token/GPU/storage/contact capacity is verified
personal devices may be used by default
private data can train routing
revenue share is legally/commercially finalized
```

Allowed claim:

```text
The repo now contains a consent-first plan to recruit 20 operators, validate
operator value, build revenue paths, and only later pool resources after explicit
per-resource opt-in.
```

## Target Math

If the target is `$4,000,000` annualized gross revenue:

```text
$4,000,000 / 12 = $333,334 monthly gross target
$4,000,000 / 20 operators = $200,000 annual gross contribution per operator
$333,334 / 20 operators = $16,667 monthly gross contribution per operator
```

That is too high for a first-pass operator fleet unless the work is high-ticket
services, enterprise contracts, or founder-led closes. The first goal is not to
pretend the average is easy. The first goal is to discover which operators can
support which revenue lane.

| Builders | 4-5 | Demos, local apps, docs, tests, automations | Working demo packets |

Nobody is required to donate device resources. The human value network comes
first. The resource pool is later and opt-in.

## Offer Ladder

Start with offers that can be sold before the full platform exists.

| Offer | Buyer | Price test | Proof needed |
|---|---|---:|---|
| BetterSafe essential-needs navigator setup | households, advocates, small orgs | $250-$1,500 | local-only packet, no authority claims |
| Lantern operator workspace setup | solo builders, creators, founders | $500-$2,500 | working local chat + docs + handoff |
| Source-backed AI safety / claim audit | teams with messy AI claims | $1,500-$7,500 | before/after claim pack |
| Operator portfolio / automation sprint | job seekers, freelancers, small teams | $1,000-$5,000 | shipped artifact + review |
| Foundry-managed delivery pod | small businesses, agencies | $5,000-$25,000/mo | repeatable delivery and support |
| Enterprise trust-first AI ops pilot | regulated or high-trust orgs | $25,000-$150,000 | security, privacy, legal review |

The first 30 days should validate willingness to pay, not optimize the full
resource-pool architecture.

## Revenue Path To 4M

Use three lanes:

| Lane | Monthly target by maturity | Notes |
|---|---:|---|
| Services / pilots | $100k/mo | Fastest path. Founder-led and closer-led. |
| Managed delivery pods | $150k/mo | 6-10 retained clients at $15k-$25k/mo. |
| SaaS / licenses / training | $83k/mo | Slower, needs proof and support loop. |

Combined mature monthly target:

```text
$100k + $150k + $83k = $333k/mo
```

This is a target model, not a forecast. Update weekly with actual calls, closes,
revenue, churn, delivery load, and operator capacity.

## First 24 Hours

1. Freeze the claim: "20-operator trust-first AI foundry, consent-first, local-first, no hidden pooling."
2. Pick the first paid offer: `Source-backed AI safety / claim audit` or `Lantern operator workspace setup`.
3. Make a buyer list of 50 warm contacts and 50 cold-but-specific targets.
4. Assign 20 operators into provisional roles; mark unfilled roles as gaps.
5. Create one public-safe demo packet and one private delivery checklist.
6. Book 10 conversations. Do not pitch resource pooling first.
7. Track every contact in a simple ledger: person, problem, offer, next step, consent notes.

## First 7 Days

- 50 direct outreach messages.
- 20 discovery calls requested.
- 10 calls completed.
- 3 paid pilot asks made.
- 1-2 paid pilots closed or explicitly lost with reasons.
- One delivery proof packet shipped.
- One redaction/safety review before any public case study.

Pass/fail:

```text
pass = at least one buyer offers money, time, or a strong referral for a concrete offer
fail = people like the story but no one wants a concrete next step
```

## First 30 Days

| Metric | Minimum | Strong |
|---|---:|---:|

| Paid pilots | 3 | 8 |
| Gross revenue | $5k | $40k+ |
| Delivery artifacts | 3 | 10 |
| Public-safe case studies | 1 | 4 |

If revenue is below $5k after 30 days, narrow the offer and sell founder-led
services before building more platform.

## First 120 Days

Goal: turn founder-led work into a delivery pod.

| Workstream | Outcome |
|---|---|
| Sales | 3 reliable offer scripts, one CRM ledger, weekly pipeline review |
| Delivery | documented pilot workflow, QA checklist, redaction checklist |
| Product | local Lantern setup, BetterSafe packet builder, source-backed review kit |
| Operators | 20-person role map, contribution ledger, training ladder |
| Proof | 5 public-safe case studies or demos |
| Resource pool | consent UX prototype only; no default pooling |

## Resource Pool Gate

Only after paid work and trust exist:

```text
~/.foundry/consent.json defaults every resource OFF
per-resource opt-in only
60-second withdrawal
visible purpose field
hard caps
local workspace only
no personal files/browser/email/webcam/PII
no remote override
```

Resource-pool success is measured by consent retention and useful work
completed, not by how much hidden capacity can be extracted.
